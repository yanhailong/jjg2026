# 小额抽奖礼包服务端

依据《小额抽奖礼包活动策划文档》实现。本次不新增、修改 Excel 配置表；没有配置源时活动不开放。客户端界面、动画和真实支付渠道联调不在当前服务端仓库内。

## 文档冲突的实现口径

- 按核心规则和服务端说明：共 14 格，13 个普通格 + 1 个大奖格。UI 章节的“14 普通 + 1 大奖”未采用。
- 大奖由玩家免费主动选择，抽中前不限次数，抽中后锁定。未采用配置说明中的“随机切换”。
- 文档没有定义权重，按剩余格子等概率抽取，不放回。
- 正式循环赛季启用，跟随其起止时间；引导赛季不启用。按循环赛季序号选择配置阶段，超过最后阶段时重复最后阶段，玩家进度仍按每期 seasonKey 重置。

## 行为

真实登录、在线跨日或认证请求记入每日登录账本，不要求进入活动页面。离线日期不补资格。同一天不重复增加，下一次登录日保留最多 3 次旧资格再增加当天 1 次；待支付预占、扣款结果不确定的资格计入上限。一天可以使用多个累计资格；奖池抽空不能再购买。

钻石、金币购买先持久化扣款意图，扣款成功后保存唯一随机结果再发奖。现金先预占资格，收到成功支付回调才抽奖。预占后仍可更换未获得的大奖，以实际抽奖时选择为准。重复请求与支付回调不会重新抽取或重复发奖。

每日免费福利独立于付费资格，服务器自然日零点重置，每天领取一次。入口红点进入后清除，下一个真实登录日重新提示；免费福利另有红点。

赛季到期清空未使用资格，不补发未领取免费福利。已获得但明确发放失败的奖励走幂等邮件；旧期订单延迟付款只在旧期快照抽奖并邮寄，不影响新期。保留未完成订单预占以处理迟到回调，没有擅自按超时取消可支付订单。

## 配置接入

后续提供一个实现 `LuckyDrawConfigSource` 的 Spring Bean，返回 `LuckyDrawDefinition` 列表；不允许将正式数值写死在服务代码中。

模型包含 activityId、连续 stageIndex（从 1 开始）、名称/图标、priceType（1 现金分、2 钻石、3 金币）、price、shopId、maxCarryDays（3）、14 个格子、大奖候选和每日福利。

普通格位置为 1–13，大奖位置为 0；格子 ID 唯一，大奖候选 ID 唯一，道具数量为正。首次创建玩家本期快照前校验道具存在、现金价格与渠道商品配置一致。每期保存完整配置快照，热更不改变已开始玩家的本期奖池和价格。各节点须使用一致的服务器时区。

## 协议

使用 SEASON 消息类型：

| 请求 | cmd | 参数 |
| --- | --- | --- |
| ReqLuckyDrawInfo | 0x2F | activityId（0 查询本期）、drawType=1、enter |
| ReqLuckyDrawBuy | 0x30 | activityId、drawType=1、requestId |
| ReqLuckyDrawSelectGrand | 0x31 | activityId、drawType=1、grandId |
| ReqLuckyDrawDaily | 0x32 | activityId、drawType=1 |
| ResLuckyDraw | 0x33 | action（1 信息、2 购买、3 切换、4 福利）、info、奖励、replay、rewardPending |

requestId 使用 1–64 位字母、数字或连字符。客户端一次购买生成一个唯一值，网络重试必须复用，下一笔购买换新值。皮肤 drawType=2 仅预留，目前拒绝购买。

现金走现有 ReqGenerateOrder，rechargeType=19，productId=`activityId_1_requestId`。服务端转换为本期预占 token，同一 token 创建唯一订单。真实渠道 SKU 独立保存到订单 channelProductId，不以业务 token 替代 SKU。回调校验玩家、金额、SKU 和 token；付款后刷新信息获取抽奖状态。

## 存储与恢复边界

Mongo 集合 `seasonLuckyDraw` 保存本期快照、资格、已抽格子、大奖选择、预占和奖励收据；`seasonLuckyDrawLogin` 以“玩家:日期”为唯一键记录实际登录日期。玩家购买、选择与回调共用 Redis 玩家锁；每分钟执行过期结算。

背包扣款/发奖与活动 Mongo 文档无法形成跨存储事务。若进程中断或接口返回不确定结果，收据停留 DEBITING/DELIVERING，禁止自动重复扣款或发奖，需依据背包流水人工对账。明确失败才允许重试或邮件补发。上线前需对接现有告警/运维对账流程，并为登录账本和到期查询设置适合实际规模的索引、归档策略。

本次验证结果：小额抽奖 21 项、连续礼包回归 22 项，共 43 项通过，0 失败；另包含 Mongo 映射往返和渠道 SKU 与业务 token 分离的订单测试。common、sampledata、core、sim 四模块在隔离副本中编译通过。

仓库现有配置生成类删除导致原始构建受阻；使用 `.tmp/continuous-gift/verify` 隔离副本，仅在副本中补齐 HEAD 基线生成类进行四模块编译和两个礼包功能测试，未恢复工作区中用户删除的类。该验证不等同于当前完整仓库构建通过，也不替代 Mongo/Redis 和真实支付渠道联调。
